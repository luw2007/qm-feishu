# Surface adapter implementation notes

- The adapter targets Node 24.18.0 locally because the workstation default Node 22 cannot satisfy the approved Node 24 engine gate.
- Shared ports use Web `ReadableStream<Uint8Array>` so surface modules remain independent of Node and vendor SDK stream types.
- Threshold defaults remain configuration fields; the 30 MB Feishu upload ceiling is a protocol limit, not an operator tuning threshold.
- The public package exports one runtime value, `startFeishuSurface`; all other public exports are TypeScript types.
- Health starts before external dependency probes: invalid configuration still fails fast, while valid processes remain live with readiness false and retry QM/Feishu connectivity.
- Runtime recovery reuses `FEISHU_DELIVERY_POLL_MS`; the removed `CORE_RETRY_COUNT` field had no consumer and would have advertised behavior the adapter did not implement.
- Approval callback continuity uses QM's persisted `PendingApprovalRecord.request`; the adapter decodes only actor, surface, delivery target, and conversation coordinates, so restart recovery needs no local state and does not expose the original message text.
- Feishu business code `99991400` is retryable even with HTTP 200/400; the pinned SDK documents it as application frequency limiting. Other nonzero business codes remain permanent unless separately documented.
- Compatibility and release CI start `yc-software/qm@7f2c916` with memory stores and run the source-auth contract without the local opt-in skip.
- Approval records in QM `7f2c916` have no status field: HTTP 200 means the record remains pending, while allow/deny deletes it and subsequent lookup returns 404. `decodeApproval` therefore maps a present wire record to `pending`; parsing a resolved status would invent an unsupported contract.
- Local release-candidate smoke used the built `dist/main.js` against pinned QM: liveness stayed 200 while synthetic Feishu credentials kept readiness at 503, metrics remained identifier-free, missing configuration failed closed, and direct Node SIGTERM exited cleanly within the configured deadline.
- Container build/inspection, the remaining dedicated-tenant live matrix, CI URLs, immutable image digest, and `v0.1.0` publication remain release gates. This workstation has working Feishu app credentials and GitHub authentication, but no container runtime, configured Git remote, or existing `luw2007/qm-feishu` GitHub repository; the live runbook remains intentionally pending rather than recording synthetic evidence.
- Live verification on 2026-08-03 confirmed direct DM, proactive principal delivery, dependency recovery, graceful SIGTERM, and transient Feishu send recovery against QM `7f2c916` and the real Feishu Bot API. The remaining user-originated matrix rows stay pending: the workstation has no active desktop session, and Feishu Web is denied by the tenant's MDM/OS conditional-access policy; bot-authored messages are not accepted as substitutes for user-originated live evidence.
- QM `7f2c916` returns a completed idempotency replay as HTTP 200 `{ status: "ok", sessionId, sourceUserSeq, sourceAssistantEntrySeq, reply }`, not a queued run. The adapter maps that narrow wire variant to `{ replayed: true }`; intake suppresses duplicate acknowledgement/cache/watcher side effects, and approval callbacks preserve success without inventing a run ID.
- Acceptance OAuth exploration created no supported user-send path. The per-app user token file was deleted. Open Platform accepted a user `im:message` deletion draft while retaining the tenant/app identity grant; `offline_access` remains an OAuth base grant. A previously created app version `1.0.6` is audited but not published, and the platform rejected hand-written release/cancel/delete requests with code `10002`; no version state change was claimed.
- A real Web Messenger group mention reached the long-connection handler on 2026-08-03 and exposed a second terminal idempotency replay shape: QM returned HTTP 200 `{ status: "silent", sessionId }`. QM's async turn path returns `queued` for new runs and exposes a terminal result only when the idempotency key resolves to an already-terminal run, so the adapter maps only `silent` with a non-empty session ID to `{ replayed: true }`; intake and approval callers suppress duplicate acknowledgements, cache writes, and watchers. Other terminal and malformed 2xx shapes remain contract errors.
- Feishu `chat.create` expects application IDs in `bot_id_list`, not bot open IDs. The acceptance app created dedicated private group `f1f983`; `chat.list`, `chat.get`, and member listing confirmed `chat_mode: "group"` and the synthetic user membership.
